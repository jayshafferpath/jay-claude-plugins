# Finalize

Final pass before merge. Updates the PR description to reflect the actual shipped state, then posts a finalization comment with context that downstream agents can use when working on stacked tickets.

> **Jira side effects, despite the missing `mcp__atlassian__*` allow-list entries**: this command touches Jira (it appends to the ticket's `[claude-activity-log]` comment) via the `append-activity` CLI rather than the Atlassian MCP server. The CLI authenticates with `JIRA_EMAIL` / `JIRA_API_TOKEN` from `.env` and posts directly through the Jira REST API. So the activity log on the ticket *will* be updated even though no MCP tool is listed.

## Step 1: Gather Context

1. Determine the base branch:
   - Try `gh pr view --json baseRefName,number,url,title -q '.'` to get the existing PR details.
   - If no PR exists, **stop** — there's nothing to finalize without an open PR.
2. Store `PR_NUMBER`, `PR_URL`, `BASE_BRANCH`, and current `PR_TITLE`.
3. Run `git log {BASE_BRANCH}..HEAD --oneline` to get commit history.
4. Run `git diff {BASE_BRANCH}...HEAD --stat` to get changed files summary.
5. Run `git diff {BASE_BRANCH}...HEAD` to get the full diff.
6. Get the current branch name: `git branch --show-current`.
7. Check for a plan file — look for `.claude/plans/jira-*.md` or `.plans/*.md` in the repo. If found, read it to understand the original plan and intended approach.
8. Read the existing PR description: `gh pr view --json body -q .body`.

## Step 2: Update PR Description

Use the Skill tool to run skill `pr-description` with args `{BASE_BRANCH}`.

After it completes, read the generated `./pr.md` file. The first line is the title, the rest is the body.

Update the existing PR. Split `./pr.md` into its title line and body, write the body to a temp file, then PATCH both fields:

```bash
gh api --method PATCH repos/{owner}/{repo}/pulls/{PR_NUMBER} -f title="{NEW_TITLE}" -F body=@{BODY_FILE}
```

Two reasons this uses the REST endpoint instead of `gh pr edit`:

- **Scope.** `gh pr edit` issues a GraphQL query that reads org-level fields (`login`, `name`, `slug`) to resolve reviewers, even when only `--title`/`--body` were passed. On a token without `read:org` it fails outright with a scopes error that looks like a permissions problem on the PR but isn't. REST PATCH needs only `repo`.
- **Quoting.** `-F body=@{file}` reads the body from a file, so backticks, `$`, and newlines in the generated description reach GitHub intact. Passing the body inline (or via `-f body="$(cat …)"`) re-introduces shell interpolation bugs.

The `{owner}`/`{repo}` placeholders are literal — `gh` resolves them from the local remote, so no slug lookup is needed.

## Step 3: Build Finalization Comment

Compose a structured comment intended for both human reviewers and downstream Claude agents working on stacked tickets. The comment should contain:

### 3a: Reasoning

Summarize the high-level reasoning behind the implementation decisions. What approach was taken and why? If a plan file exists, compare the final implementation against the plan — note where the implementation followed the plan and where it diverged.

### 3b: Deviations from Plan

If a plan file was found in Step 1, list any deviations:

- Tasks that were skipped and why
- Tasks that were implemented differently than planned
- Additional work that wasn't in the original plan
- Scope changes (things added or removed)

If no plan file exists, note "No plan file found — deviations cannot be assessed."

### 3c: Files Changed and Why

For each changed file (from `git diff --stat`), provide:

- **File path**
- **What changed**: 1-2 sentence summary
- **Why**: The reason this file needed to change in the context of this PR

Group related files together (e.g., "API Layer", "Data Layer", "Tests") when there are more than 10 files.

### 3d: Context for Downstream Tickets

Identify information that agents working on tickets stacked on top of this branch need to know:

- New patterns, utilities, or abstractions introduced that should be reused
- API or interface changes that downstream code must conform to
- Schema or model changes that affect downstream work
- Configuration or environment changes
- Any known limitations or TODOs left intentionally for downstream tickets

## Step 4: Post the Comment

Compose the comment body to a temp file (`./.claude-finalize-comment.md` or similar) using this template:

```markdown
## Finalization Summary

### Reasoning
{reasoning from 3a}

### Deviations from Plan
{deviations from 3b}

### Files Changed
{file summaries from 3c}

### Context for Downstream Work
{downstream context from 3d}

---
_Generated by `/finalize` — intended as context for reviewers and downstream agents._
```

Post it to the PR with `gh pr comment {PR_NUMBER} --body-file <temp.md>`.

If a Jira ticket key can be inferred from the branch name (e.g., `PROJ-123-feature`), also append a compacted version (4-8 lines max — one-line reasoning, count of changed files grouped by area, key downstream-context bullets) to the ticket's activity log via `append-activity {TICKET_KEY} --heading "Finalized" --body-file <compact.md>`. The full narrative stays on the GitHub PR.

## Step 5: Summary

Display:

```
Finalized PR #{PR_NUMBER}: {PR_TITLE}
{PR_URL}

- PR description updated
- Finalization comment posted
```
